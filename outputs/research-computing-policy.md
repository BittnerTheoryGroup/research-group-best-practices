# Research Computing and Paper Production Policy

## Purpose and governing principle

This policy makes computational work trustworthy without treating every scratch calculation like a publication. Requirements increase with the claims made for a result. Work must be promoted deliberately from **exploratory** to **validated** to **publication-level**. An explicit request such as “make this publication-ready,” use in a submitted manuscript, or designation as a final numbered figure or computational table activates the publication-level requirements.

These are minimum group standards. Applicable law, ethics approvals, funder rules, data-use agreements, journal policies, and domain standards take precedence.

## Work levels

| Level | Intended use | Minimum practice | Promotion gate |
|---|---|---|---|
| **Exploratory** | Learning, debugging, hypothesis generation, disposable trials | Keep enough context to understand the result during active work; label provisional outputs; protect sensitive data | Promote before others rely on the result or it supports a scientific decision |
| **Validated** | Internal decisions, collaborator sharing, talks, preliminary reports, results expected to persist | Version-controlled analysis; recorded inputs, parameters, environment, and seed policy; independent checks proportional to risk; retained machine-readable outputs | Promote before submission, public release, or designation as a final paper artifact |
| **Publication-level** | Manuscripts, theses, formal reports, public datasets/software, final numbered figures and computational tables | Complete production, audit, review, documentation, and archival requirements below | Release only after the publication checklist and designated review are complete |

Promotion is prospective: exploratory work need not meet later standards retroactively, but any result being promoted must be regenerated or reconstructed under the stricter level. If reconstruction is impossible, disclose that limitation and do not present the result as fully reproducible.

## Requirements by level

### Exploratory work

- Notebooks, interactive sessions, ad hoc scripts, and temporary outputs are acceptable.
- Use descriptive names when work may survive the day; record critical assumptions that would otherwise be forgotten.
- Mark plots and tables `exploratory`, `draft`, or equivalent when confusion with final results is plausible.
- Do not cite an unexplained screenshot, copied value, or interactive state as a final result.
- Do not commit secrets, credentials, regulated data, or disallowed source data. Follow the project data-management plan at all levels.
- Delete or retain scratch work according to its value and the project’s retention obligations; no general requirement mandates preserving every failed trial.

### Validated work

In addition to the above:

- Put consequential code, configuration, documentation, and small permitted inputs under version control.
- Record input identifiers or checksums, software/runtime versions, key parameters, units, preprocessing choices, and hardware details when they can affect results.
- Use an environment specification or lockfile appropriate to the ecosystem. Containers may supplement, but should not replace, readable build specifications.
- Make stochastic work reproducible where scientifically appropriate: record seeds and random-number-library versions; derive and record per-run seeds for parallel work. If nondeterminism is intrinsic or unavoidable, characterize variability with repeated runs or tolerances.
- Retain the machine-readable results needed to audit central claims; avoid relying only on rendered images or formatted tables.
- Perform at least one meaningful check, such as an analytical limit, benchmark, unit/integration test, alternative implementation, convergence study, invariant, or second-person spot check.
- Record known limitations, failed validation checks, and deviations from the intended method.

### Publication-level work

Publication-level work must satisfy all validated-work requirements plus the following.

#### Production scripts and provenance

- Every final numbered computational figure and table must be generated by a dedicated, checked-in, non-interactive production driver, for example `scripts/figures/generate_figure_2.py` or `scripts/tables/generate_table_1.R`.
- Shared numerical logic belongs in import-safe modules; drivers should mainly declare inputs, parameters, and outputs. Final artifacts must not depend solely on a notebook, manual plotting, undocumented shell history, or copied values.
- Drivers must encode or read versioned configuration for the exact model, parameters, grids, seeds, normalization, labels, dimensions, and filenames used in the manuscript. They should accept an output-directory option when practical.
- Each driver must write the rendered artifact and compact machine-readable source data sufficient to audit or replot it. Use open, documented formats where practical (for example CSV/TSV, JSON, HDF5, NetCDF, or Parquet); include a data dictionary, schema, units, and provenance.
- Preserve raw source data when permitted and practical. Otherwise retain an immutable identifier, checksum, access instructions, and the code/configuration that derives analysis-ready data. Never redistribute data contrary to consent, license, contract, or law.
- Generated artifacts should carry or be accompanied by provenance linking them to the code version, input versions/checksums, configuration, and generation time. A machine-readable manifest is preferred.

#### Reproduction and verification

- Provide one documented top-level command or workflow that regenerates all final computational artifacts when practical. Document exceptions such as costly HPC runs and provide staged instructions and retained intermediate data.
- Run production drivers in a clean environment from documented inputs. Confirm expected files exist, machine-readable outputs parse, required values are finite, and invariants, tolerances, and row/count expectations hold.
- Inspect every final figure and compiled table/manuscript visually. Check labels, units, legends, colors, accessibility, cropping, resolution, font sizes, significant figures, pagination, and consistency with captions.
- A qualified person other than the primary producer must review central claims and high-risk artifacts. At minimum, the reviewer checks the command path, provenance, principal parameters, numerical sanity, and agreement between artifact, caption, and prose. Full independent recomputation is strongly preferred for central or surprising claims and may be required by the project lead.
- Verify manuscript descriptions against implementation: equations, conventions, parameter values, sample sizes, exclusions, uncertainty definitions, normalization, plotted quantities, filenames, and reported numbers must agree. Resolve discrepancies rather than merely documenting them.

#### Documentation and release

- Maintain a README or reproduction guide stating scope, prerequisites, data access, environment creation, exact commands, expected outputs, approximate runtime/resources, validation checks, and known limitations.
- Include a license where the group has authority to do so, contributor/author information, and citation metadata such as `CITATION.cff`. State restrictions clearly when code or data cannot be open.
- Use meaningful commits and peer-reviewed changes for publication-critical code. Tag the exact submitted and accepted states (for example `paper-v1.0-submitted` and `paper-v1.1-accepted`); do not rewrite released history.
- **Create one GitHub repository for each published paper.** The repository is the paper’s working computational record and must contain, or unambiguously retrieve, the data and scripts needed to reproduce every published computational figure. Include final computational tables and reported numerical claims when applicable.
- Organize the paper repository so that each published figure maps clearly to its production driver, required input data, machine-readable source data, and expected output. The README must give exact reproduction commands and identify any prerequisites that are not included.
- **Archive a versioned release of the paper repository with Zenodo and obtain a DOI.** The Zenodo record must capture the exact code, permitted data, source-data tables, environment metadata, and documentation used for the published paper. Cite the version-specific Zenodo DOI in the paper and add the paper DOI to the GitHub/Zenodo metadata after publication.
- Verify the archived package itself: retrieve or inspect the Zenodo deposit, confirm expected files and metadata are present, and test reproduction from the archived release rather than relying only on the live GitHub checkout.
- GitHub is the working record; the Zenodo release is the preservation record. If data cannot legally or ethically be deposited, the repository and archive must still contain all distributable scripts plus an immutable data identifier or precise access procedure, checksums where permitted, a description of the unavailable data, and a documented test or synthetic dataset sufficient to exercise the workflow. Record the restriction as an approved exception; do not silently omit inputs.

## AI tools, confidentiality, and potential intellectual property

AI assistants can improve research workflows, but sending material to a hosted model is an external disclosure and processing event governed by the institution’s agreements, account configuration, and the specific product and connected tools. A provider’s allocation of ownership in inputs or outputs does not by itself preserve patent rights, establish inventorship or authorship, guarantee confidentiality, ensure output uniqueness, or clear third-party rights.

This is a rapidly developing legal and professional area. The absence of a settled legal rule, a documented prior misuse, or model-training use does not make disclosure risk-free. Research priority, trade-secret status, patent filing strategy, contractual confidentiality, reputational credit, and the practical ability to prove independent contribution may be affected before a court or institution resolves ownership. The group therefore uses a precautionary standard for frontier, commercially valuable, or priority-sensitive research.

- **Classify before disclosure.** Before entering unpublished inventions, enabling technical details, source code, grant concepts, confidential collaborations, embargoed results, or proprietary datasets into an AI system, determine whether the material is public, internal, confidential, export-controlled, regulated, contract-restricted, or potentially patentable.
- **Use only approved services and accounts.** Potentially valuable or confidential material may be processed only through institutionally approved AI services, accounts, models, features, and retention settings whose terms and security controls have been reviewed for that data class. Personal/free accounts are not an acceptable substitute. “Not used for model training” is not the same as zero retention or no human/third-party access.
- **Disable training use.** Group members must turn off any setting that permits OpenAI—or another AI provider—to use their chats, files, prompts, or outputs for model training or improvement on every account used for research. Members must not opt into voluntary data sharing, feedback sharing, or evaluation sharing with research content. For institutionally managed and API accounts, the designated administrator must verify and periodically audit the organization- and project-level settings; do not rely only on provider defaults.
- **Minimize disclosure.** Provide the least information needed; redact names and sensitive details; use synthetic, abstracted, or local test data where possible. Do not send complete invention disclosures, unpublished patent claims, credentials, restricted data, or third-party confidential information unless specifically authorized.
- **Check the whole data path.** Connectors, plug-ins, browsing, remote tools, file stores, feedback buttons, logging, prompt caching, and subprocessors may have policies different from the core model. Disable unneeded features and verify where prompts, files, outputs, and telemetry are stored and for how long.
- **Seek review before high-risk use.** Consult the principal investigator/project lead and the institution’s technology-transfer, research-security, privacy, or legal office before disclosing potentially patentable subject matter or information governed by an NDA, sponsored-research agreement, material/data-use agreement, export controls, or human-subject protections. File invention disclosures before external disclosure when advised.
- **Protect research priority.** Treat unpublished enabling ideas, proof strategies, negative results, research road maps, and detailed notes for highly competitive or landmark problems as confidential even when they are not yet recognized as patentable. Until publication or explicit clearance, prefer approved local/offline models or provide only compartmentalized, non-enabling questions to hosted systems.
- **Keep an appropriate AI-use record.** For validated or publication-level work, record the service/product, account class, model/version when available, date, purpose, material categories disclosed, relevant data-control setting, and substantive human verification. Store prompts/outputs only when permitted; when their contents are sensitive, record a restricted audit reference or summary instead of committing them to the research repository.
- **Treat output as untrusted assistance.** Human researchers remain responsible for scientific claims, citations, code, originality, licensing, and compliance. Review output for confidential material, fabricated content, close imitation, license incompatibility, and third-party IP. Do not assume output is unique or eligible for copyright or patent protection.
- **Preserve human contribution evidence.** Keep dated design notes, commits, experimental records, and decision logs that show the researchers’ conception, selection, modification, and validation of important intellectual contributions. Do not list an AI system as an author or inventor; refer questions of human authorship or inventorship to applicable journal, funder, institutional, and legal rules.
- **Preserve the governing record.** For high-risk projects, retain an approved, access-controlled snapshot of the applicable service terms, privacy/data-control documentation, institutional approval, and account settings alongside the AI-use log. Provider policies may change; the relevant question is what governed the specific use at the time.
- **Escalate incidents promptly.** If protected information is entered into an unapproved system, stop further disclosure, preserve necessary facts without spreading the content, and notify the designated institutional security/privacy and technology-transfer contacts. Do not attempt concealment or unilateral deletion as a substitute for incident handling.

The group must maintain a short approved-AI-use matrix listing permitted services/account types, allowed data classifications, training and retention settings, enabled third-party tools, responsible owner, and review date. The matrix must designate who verifies that training/improvement sharing remains disabled. Because law, service terms, and controls change, verify the matrix at least annually, after a material provider-policy change, and before a new high-risk use. This policy is risk management, not a legal conclusion; institution-specific legal and technology-transfer advice controls.

## Recommended project layout and naming

Adapt this layout to disciplinary norms, but keep raw inputs, code, generated results, and manuscript assets distinguishable:

```text
project/
├── README.md
├── CITATION.cff
├── LICENSE
├── environment/          # lockfiles, environment specs, container definitions
├── config/               # versioned run and production configurations
├── data/
│   ├── raw/              # immutable or external/read-only; often not in Git
│   ├── interim/
│   └── processed/
├── src/                  # reusable, import-safe scientific logic
├── notebooks/            # exploration and narrative diagnostics
├── scripts/
│   ├── figures/          # generate_figure_1.*, ...
│   └── tables/           # generate_table_1.*, ...
├── tests/
├── results/              # machine-readable results and provenance manifests
├── manuscript/
└── artifacts/            # generated figures/tables; draft and final separated
```

Use stable names that reflect manuscript identifiers. Avoid ambiguous names such as `final2`, `new_results`, or dates as the only versioning mechanism. Use Git and release tags for versions; use dates in run directories only when they aid operations. Generated files should not be hand-edited.

## Responsibilities

- **Artifact owner:** classifies the work, preserves provenance, executes checks, and reports limitations.
- **Reviewer:** examines scientific and computational correctness at a depth proportional to claim risk and records approval or unresolved concerns.
- **Paper lead/corresponding author:** confirms all final artifacts have owners and reviewers, resolves exceptions, approves the release manifest, and ensures citations and deposits match the manuscript.
- **Group/project lead:** supplies infrastructure and training, sets retention/access rules, and prevents compliance work from falling invisibly on junior members.

Authorship and review are distinct: being an author does not automatically constitute artifact review, and review does not by itself confer authorship.

## Exceptions and proportionality

An exception is acceptable when a requirement is impossible, unethical, legally barred, scientifically inappropriate, or grossly disproportionate—for example, licensed clinical data, proprietary instruments, irreproducible external services, nondeterministic hardware, or prohibitively expensive simulations. Before release, record:

1. the requirement not met and why;
2. the risk to verification or reuse;
3. the compensating evidence (checksums, synthetic data, pseudocode, retained outputs, tolerance studies, access committee, or independent review);
4. the approving project lead and date.

Exceptions must be visible in the reproduction guide and, when material, in the manuscript’s availability or limitations statement. They are not a mechanism for avoiding ordinary cleanup.

## Adoption checklist

### Group setup

- [ ] Name a policy owner and review the policy annually.
- [ ] Establish the one-GitHub-repository-per-paper and Zenodo DOI workflow, including repository ownership, release naming, and offboarding arrangements.
- [ ] Publish templates for repository layout, artifact manifests, reproduction guides, and exception records.
- [ ] Define data classification, access, backup, retention, and offboarding rules.
- [ ] Train members on Git, environments, testing, seed handling, licensing, and deposits.
- [ ] Publish and annually review an approved-AI-use matrix, disclosure rules, and incident contacts with institutional technology-transfer, security, privacy, and legal guidance.
- [ ] Confirm that training/improvement and voluntary feedback/data-sharing settings are disabled on all research-use AI accounts; assign an administrator to audit managed accounts and projects.
- [ ] Pilot the workflow on one active paper and revise it from observed costs.

### Per-project initiation

- [ ] Assign project, data, artifact, and review responsibilities.
- [ ] Record legal/ethical/data-use constraints and the planned archive.
- [ ] Identify potentially patentable or confidential material and decide whether, where, and under which account/data controls AI tools may be used.
- [ ] Establish version control, environment capture, naming conventions, and storage locations.
- [ ] Create or designate the paper’s GitHub repository and plan how all figure inputs will be included or retrieved.
- [ ] Define what evidence promotes work from exploratory to validated.

### Publication gate

- [ ] Inventory every final computational figure, table, and reported numerical claim.
- [ ] Confirm each artifact has a checked-in driver, source data, provenance, and owner.
- [ ] Regenerate artifacts using documented commands in a clean environment.
- [ ] Complete numerical, visual, and manuscript/code consistency checks.
- [ ] Record reviewer sign-off and approved exceptions.
- [ ] Review AI-use records for unauthorized disclosure, third-party rights, and required acknowledgments; resolve IP questions with the institution before public release.
- [ ] Confirm the paper has its own GitHub repository and that every published computational figure maps to included scripts and included or precisely retrievable data.
- [ ] Tag the exact paper release, archive it with Zenodo, obtain and cite the version-specific DOI, and verify the archived package and metadata.

## Reference basis

This policy is informed by the FAIR principles’ emphasis on persistent identifiers, rich metadata, provenance, licensing, and reuse; the practical principle that data should be as open as possible and as closed as necessary; and current guidance on software archiving and AI data controls. OpenAI’s API documentation, for example, distinguishes non-training commitments from abuse-monitoring and application-state retention, and notes that data sent to remote third-party tools is governed by those services’ policies. Product-specific controls and institutional agreements must be checked rather than generalized across AI services. See [GO FAIR Foundation: FAIR principles](https://www.gofair.foundation/fair-principles), [GO FAIR Foundation: FAIR assessment](https://www.gofairfoundation.org/certification/fair-assessment/), [Zenodo: GitHub and software](https://help.zenodo.org/docs/github/), [GitHub Docs: referencing and citing content](https://docs.github.com/en/repositories/archiving-a-github-repository/referencing-and-citing-content), and [OpenAI API documentation: data controls](https://developers.openai.com/api/docs/guides/your-data).
